## 2. 和设计文档不同的地方

| 设计 | 实际 | 原因 |
|---|---|---|
| 会话令牌存 Redis | 存 MySQL（`pa_session`，只存 sha256） | 一家人的访问量，MySQL 足够；M1 少一个启动依赖。M2 做后台任务队列时再接 Redis |
| 领域包互不 import | `chat` 作为编排层直接用 family / memory / bot / llm；其余领域包互不引用 | `chat` 位于依赖图顶端，不会成环，省掉一层 ports 适配 |
| L1 常驻上下文每轮注入系统提示词 | **会话开始时冻结**系统提示词和工具列表；每轮检索结果作为当轮用户消息的第一个文本块追加 | 见下一节 |
| 手机端用 antd | 用 antd-mobile | 设计文档第 11 节已确认 |

## 3. 对话上下文为什么这样组织

Claude Opus 5.5 的 thinking 块签名绑定了它之前的完整对话前缀（系统提示词、工具列表、之前的每条消息）。**只要改过前面的任何内容，之前的 thinking 就全部失效**，新账号会直接报 400；同时提示词缓存也全部作废。

所以对话历史严格「只追加」：

```
system   = 机器人提示词 + 家庭成员 + 几个家 + 关系要点 + 常驻记忆   ← 首条消息时生成，存 pa_conversation.system_snapshot，之后不变
tools    = 机器人的工具列表                                        ← 同上，存 tools_snapshot
messages = [
  user:      <turn_context>当前时间 + 本轮检索到的记忆</turn_context> + 我的话   ← 检索结果跟着这一轮落库，之后不变
  assistant: 原生内容（含 thinking 及签名）原样保存在 pa_message.raw，续聊时原样回传
  tool:      工具结果
  ...
]
```

代价：会话进行中新加的记忆不会出现在这个会话的「常驻记忆」里，但会在下一轮的 `<turn_context>` 检索中出现，助理也能用工具查到。想要全新的常驻上下文，开一个新对话即可。

兜底：如果 Claude 仍然报 thinking 签名错误，网关会去掉历史里的 thinking 块重试一次（这一轮模型拿不到之前的推理过程，但对话不中断）。这条路径有单元测试覆盖。

## 4. 记忆进入「待确认」的规则

| 来源 | 状态 |
|---|---|
| 管理端 / 手机端速记手工录入 | 直接生效 |
| 助理在对话中记录，置信度 ≥ 0.8 | 直接生效 |
| 助理推断的（置信度 < 0.8） | 待确认 |
| 要替代旧记忆的（她变了） | 待确认；确认时才把旧记忆标为「已过时」 |

## 5. 验证情况

- Go：`go vet` 全部通过；单元测试覆盖迁移分句、Claude 流式 + 工具调用往返（用模拟服务器验证 thinking 签名原样回传、历史前缀字节一致、签名失效时去掉 thinking 重试）、OpenAI 兼容协议流式工具调用拼接、向量化排序与归一化、向量索引、时间衰减、记忆默认值、认人、记忆格式化。
- 前端：两个应用 `tsc --noEmit` 和 `next build` 均通过。
- **还没有在真实 MySQL 和真实 Claude API 上联调**（开发机上没有数据库连接和 API Key）。首次启动请按 README 配置，注意观察迁移和第一轮对话的日志。
