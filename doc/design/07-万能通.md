# 07 · 万能通

一个专门「帮我想起来」的机器人：**东西放哪了、发生过什么、谁说过什么**。外加两种录入方式：拍照说一句记下东西，以及在 App 里随手录，所有内容都先交给大模型清洗，再写进记忆。

## 0. 范围

| # | 需求 | 做法 | 状态 |
|---|---|---|---|
| 1 | 拍照或选图，说清是什么、干什么用、放在哪；以后一问就能找到，还能翻出原图 | 照片存为原始记录的附件（阿里云 OSS）→ 视觉模型和我的说明一起抽成「物品」记忆 → 文字向量 + 全文检索 → 回答里引用到它就显示原图 | ✅ |
| 2 | 随时在 App 里录各种内容，经大模型清洗后进记忆 | 速记新增「随手录」（默认页）：文字或键盘听写 + 照片，走现有的抽取管线 | ✅ |
| 3 | 查发生过的事、说过的话 | 万能通用 `search_memory` 查事件、原话，回答带编号和时间 | ✅ |
| 4 | 对话里说话 | 录音 → MiniMax `asr-1.0` 转文字 →「转成文字」填进输入框，或「直接发送」给模型。见 §6 | ✅ |

## 1. 存储：为什么不单独上向量库

| 数据 | 放哪 | 理由 |
|---|---|---|
| 原图 | **阿里云 OSS 私有桶**，路径 `notes/{family}/{note}/{i}.jpg` | 图片不进数据库；桶不公开，手机经 app-api 带登录转发读取（`GET /api/notes/:key/attachments/:i`） |
| 照片和录入时说的话 | `pa_source_note`（原始记录，只增不改） | 和截图、粘贴的聊天走同一个入口，`channel=capture` |
| 「这是什么、放哪」 | `pa_memory`，新类型 **`item`（物品）** | 结构化字段放在 `attrs` 里：`location`（从大到小）、`usage`、`photos:[{note,index}]` |
| 向量 | `pa_memory_embedding`，进程内算余弦 | 和现有记忆共用一套 |

**做法是先把照片描述成文字，再对文字做向量。** 抽取时让视觉模型把照片里看到的写进 `content`（名称、品牌、颜色、外观、上面的字），再加上我说的用途和位置。之后对这段文字做 embedding，同时进 ngram 全文索引。以后我用「蓝色那个盒子」「充电头」这些不同叫法来问，都能命中。

不做的：

- **不存图片向量（比如 CLIP）。** 「找东西」的问题都是用文字问的，图片向量对中文口语描述的召回不如「照片 → 文字描述 → 文字向量」。真要「拿照片找东西」，也是先把这张照片描述成文字再检索，走同一条路。
- **不单独上向量库（Milvus、Qdrant……）。** 家庭这个量级只有几千到几万条，内存里暴力算余弦不到 10 毫秒（见 01 · 1.1）。多一个组件就多一份运维，还要在 MySQL 和向量库之间做双写一致性。`memory.vectorIndex` 已经抽象成接口，量真的大了再换也来得及。

**东西挪了地方**：新记一条物品记忆，替代旧的（`supersedes_key`）。旧位置标成「已过时」，留在替代链里，所以问「以前放在哪」时还能看到挪动的轨迹。和「她变了」不同，挪东西是日常小事，**物品的替代直接生效，不用进待确认**（我明确说了的才这样；模型没把握的仍然进待确认）。照片和用途沿用旧记忆的。

## 2. 流程

### 2.1 在万能通里拍照

```
手机：选照片（压成 JPEG）+ 说明（键盘听写）
  │ POST /api/notes  channel=capture, inline=1   → 原始记录落库，照片写 OSS，不唤醒后台 worker
  │ POST /api/conversations/:key/messages {text, noteKey}   (SSE)
  ▼
chat.Send
  ├─ emit status「正在看照片、整理成记忆…」
  ├─ intake.ProcessNow(noteKey)：当场抢占这条记录、跑抽取（视觉 + 去重比对），被 worker 抢先就等它跑完
  ├─ 把整理结果写成 <attachment> 块，放进这一轮我的消息里（只有文字，没有图片）
  └─ 模型照着整理结果简短确认「记下了：电钻 → 阳台储物柜下层 [mem_x]」，位置没说清的追问一句
```

- 对话历史里不放图片，只放整理结果的文字。这样省 token，历史也保持只追加、不改动。
- 这一轮我的消息在 `meta.attachment` 里记下原始记录的编号、照片张数和整理出的记忆，手机端在气泡上方显示照片。
- 对话自动学习（06 · 2）会跳过带照片的消息，因为它们已经和照片一起整理过一次了。
- 整理失败时，照片仍然留着，回答会如实说「照片存好了，稍后自动重试」；后台 worker 会接着重试。

### 2.2 找东西 / 回忆

万能通的工具：`search_memory`、`get_person`、`get_place`、`list_upcoming`、`remember`、`now`。提示词要求：

- 第一句直接说在哪，带记忆编号。一次查不到，就换用途、外观、类别再查一两次。
- 记录比较旧的，提醒「可能挪过」。问「以前放哪」时，用 `include_history`。
- 查不到就直说没记过，不猜。
- 不负责出主意，「该怎么办」类问题引导去找私人助理。

**回答里显示原图**：回答结束时，服务端把引用到的记忆里的照片引用写进回答的 `meta.photos`（最多 9 张）。手机端在回答下面显示缩略图，点开看大图。给模型看的记忆文本里去掉了照片引用，只写「有 N 张照片」。

### 2.3 随手录（速记页默认页）

一个大输入框（提示可以用键盘 🎤 听写）+ 拍照 / 相册 +「关于谁」（可不选）+ 时间。提交到 `POST /api/notes`（`channel=capture`），后台 worker 整理：认人、换算日期、拆成多条记忆、去重，没把握的进「今天」待确认。原来的「记一条」（手选类型、直接生效）和「聊天 / 截图」保留。

## 3. 配置

`app-api` 和 `manager-api` 的 `application.properties` 都要配，两边必须一样：

```properties
storage.oss.region=cn-shanghai
storage.oss.endpoint=oss-cn-shanghai-internal.aliyuncs.com   # 同地域 ECS 走内网；不填用公网
storage.oss.bucket=你的私有桶
storage.oss.access_key_id=
storage.oss.access_key_secret=
storage.oss.prefix=private_assistant
```

- `bucket` 留空时，照片继续存本机 `storage.dir`。
- 切到 OSS 以后，新附件只写 OSS；读不到时会去 `storage.dir` 找，所以以前的截图不用搬。
- 建议给这两个服务开一个 RAM 子账号，权限只给这个桶、这个前缀的 `PutObject` 和 `GetObject`。

模型路由（迁移 0010 写入，管理端「模型」里可改）：

| 任务 | 默认 | 说明 |
|---|---|---|
| `chat.recall` | `claude-sonnet-5-5`，effort low | 万能通对话。找东西要的是快，不需要深度推理 |
| `memory.extract` | 沿用现有配置 | 看照片需要支持图片输入的模型。现在是 Haiku 4.5，支持图片；换成国内模型时要选多模态的 |

## 6. 语音输入（2026-10-13 补充）

一开始定的是只用 iPhone 键盘听写；后来改为接入 MiniMax 语音识别（[speech-to-text](https://platform.minimax.cn/docs/api-reference/speech-to-text)），可以说一段长话。

```
麦克风按钮 → 录音面板（音量、计时，最长 5 分钟）
  │ iPhone / 新版 Chrome：MediaRecorder 录 m4a（AAC），一分钟不到 1MB
  │ 只能录 webm 的浏览器：自己采样编码成 16kHz 单声道 WAV（识别服务不认 webm）
  ▼ POST /api/speech/transcribe（multipart audio）→ llm.Gateway.Transcribe（路由 asr）
  ▼ {"text": "..."}
「转成文字」：填进输入框，改完再发（识别偶尔会听错人名）
「直接发送」：识别完立刻发给模型（输入框里已经有字的，接在后面一起发）
```

- 录音只用来识别，**不保存**。
- 路由 `asr`（迁移 0011）默认指向 `minimax` 提供商、模型 `asr-1.0`，和对话共用一个 Key：提供商地址里带 minimax 时，自动换成 `{host}/v1/speech_to_text`。要换别家，就把 `asr` 指向 OpenAI 兼容的提供商，会调 `{base_url}/audio/transcriptions`。两种接口都是 multipart（model + file），返回 `{"text"}`。
- 管理端「模型 → 测试」对 `asr` 发一秒静音，用来检查 Key、地址和模型名对不对。
- 入口（所有和模型对话的地方都有）：
  - 手机端：机器人对话页（私人助理、万能通、三个分身共用），🎤 在输入框左边；速记「随手录」右上角。
  - 管理端：人设卡 →「对话补充」，「生成草稿」左边的「说话」按钮，录音时按钮变成一条录音栏。管理端的「对话」页只能回看记录，没有输入框。
- 两个 API 都有 `POST /api/speech/transcribe`，校验和调用都在 `llm.Gateway.TranscribeUpload`。录音逻辑 `lib/recorder.ts` 在 app 和 manager 各放一份，内容相同。
- 实测（2026-10-13）：同一段中文，wav 和 m4a 都一字不差。

## 7. 向量化接 MiniMax embo-01（2026-10-13 补充）

MiniMax 新版文档里已经没有向量化接口，但老接口 `embo-01` 仍然可用，和对话共用一个 Key，不需要 GroupId：

```
POST https://api.minimax.cn/v1/embeddings   {"model":"embo-01","texts":[...],"type":"db"|"query"}
→ {"vectors":[[...1536 维]], "base_resp":{"status_code":0}}
```

- 实现在 `service/llm/minimax.go`：提供商地址带 minimax 时走这里，只取 host，所以填 `/anthropic` 地址也能用。每批 16 条，向量归一化后存储。出错时 HTTP 状态码仍是 200，要看 `base_resp.status_code`。
- **存入和检索的编码方式不同**：存记忆用 `db`（`Gateway.Embed`），检索的问题用 `query`（`Gateway.EmbedQuery`，`memory.Search` 在用）。
- 迁移 0012：`embedding` 路由原来指向的提供商不存在、并且已经配了 minimax 时，切到 `minimax / embo-01`。
- 实测：6 条不同类型的记忆配 6 个换了叫法的问题，全部排第一，第一名比第二名高 0.3 以上：「充电头」→ 电源适配器，「打孔的工具」→ 电钻，「出国要用的证件」→ 护照，「孩子挑食」→ 不吃胡萝卜。
- 风险：这个接口已经不在文档里，以后可能下线。下线的话把 `embedding` 路由换成通义 `text-embedding-v3` 或自建 bge-m3 就行，换模型后启动时会自动全量重算。

### 换向量模型

在管理端「模型」里改 `embedding` 路由就行，不用改代码：
- 每条向量都记了 `model`。检索只用当前模型的向量，不会和别的模型的向量混着比。
- 保存 `embedding` 路由后，会自动在后台补算全部记忆的向量，覆盖旧向量；启动时也会补算一次。补算完成前，检索暂时退化为「全文 + 结构化」，不会报错。
- 两个 API 进程各有一份内存向量索引，每 30 秒从库里增量同步一次，所以对方进程算出的向量最多 30 秒后就能用上。
- 周度「重复记忆」的阈值 0.92 是按相似度定的，不同模型的分数分布不一样，换模型后可能要调。

## 8. 向量存本地文件（2026-10-13 补充）

向量化继续调远端（MiniMax embo-01），**算出来的向量存服务器本地文件，不再存 MySQL**；检索一直都是进程内存里算的。整个检索不依赖向量数据库，也不读 MySQL 里的向量。

| 环节 | 在哪 |
|---|---|
| 文字 → 向量 | 远端（MiniMax）：存记忆时一次，每次检索把问题转一次 |
| 向量存储 | 服务器本地 `{storage.dir}/vectors/{家庭}/{模型}.vec`（`vector.dir` 可改） |
| 相似度计算 | app-api / manager-api 进程内存，精确余弦 |

- `memory.VectorStore` 接口，有两种实现：`FileVectorStore`（默认）和 `MySQLVectorStore`。配置 `vector.store=mysql` 可以切回 MySQL。
- 文件格式：只追加的二进制日志，每条记录带 CRC。写用 flock 排他锁，读用共享锁，两个进程各自记读到的偏移量，每 30 秒增量读一次。崩溃留下的半条记录读的时候跳过、启动时截掉；同一条记忆的重复记录超过一半时，启动时压缩重写（写临时文件再改名）。
- 第一次切到文件时，把 `pa_memory_embedding` 里当前模型的向量导进文件，不用重新调接口。线上已导入 2 条，那张表以后不再写入。
- 备份：向量都能用记忆原文重新算，文件丢了重启会自动补算，所以不备份也行。
- 文件大小：一条 1536 维约 6KB，1 万条约 60MB。

## 9. 检索优化（2026-10-13）

每轮自动检索（L2，`service/chat/retrieve.go`）现在的流程：

```
我这句话 ──有上文？──▶ 改写成 1~3 个独立检索词（chat.query，补全「那户口本呢」这类指代）
   │
   ├─ 每个检索词并行做混合检索（memory.Search），不套门槛，合并取前 20 条
   ├─ 原文片段（原始记录切段的向量，memory.SearchPassages）取前 5 段
   ▼
重排（chat.rerank）：模型从候选里挑出真正相关的排在前面
   ├─ 重排挑中的排前面（可以把被门槛误杀的捞回来），分数门槛放行的接在后面：重排不负责删
   └─ 没配路由或调用失败：只用分数门槛（memory.Focus）
   ▼
<turn_context>：可能相关的记忆 + 原始记录里的原文（[note_xxx]，手机上点「原文」能看原始记录）
```

| 改动 | 位置 | 解决什么 |
|---|---|---|
| 改写检索词 | `chat/retrieve.go` `rewriteQueries`，路由 `chat.query`（迁移 0013） | 追问时的指代、省略 |
| 相关度门槛 | `memory/search.go` `relevant` / `Focus` | 不再每轮固定塞 12 条；没有答案时不硬塞 |
| 打分权重 | 向量 0.55、全文 0.08、重要度 0.10、新近 0.10、人物 0.10 | 字面沾边的不再压过语义真正对上的 |
| 向量文字带元数据 | `memory/vector.go` `embeddingText`，存储键 `embo-01@t2` | 「妈说过……」「放在书房的……」也能语义匹配；格式改了自动全量重算 |
| 原文兜底 | `memory/passage.go`，存储键 `embo-01@t2-notes` | 整理成记忆时漏掉的细节 |
| 模型重排 | `chat/retrieve.go` `rerank`，路由 `chat.rerank`（迁移 0014） | 门槛分不出的情况：同类但不是问的那个、向量分偏低但确实相关 |

分身（老婆 / 妈妈 / 女儿）不检索原文：原文里可能有和她无关的人和事。

### 检索评测

```bash
cd server/eval && go run . -retrieval -label "这次改了什么"
```

- 用例在 `eval/retrieval/cases.json`：45 条，分为找东西、原话、事情、偏好健康、追问、原文兜底、无答案；测试数据在 `eval/fixture.json`，是虚构的家庭（43 条记忆、4 条原始记录）。
- 只测检索，不让模型回答；直接调用 `chat.Retrieve`，和对话里走的是同一套代码。
- 模型配置（向量模型、改写和重排用的模型）从线上库只读复制，所以测出来的是线上真实效果。
- 报告写在 `eval/reports/retrieval-*.md`：按类别统计的命中率，以及每条用例的名次、前 5 名和各自的向量分、全文分。

结果（MiniMax embo-01 + M3）：

| 阶段 | 第 1 名命中 | 前 3 命中 | 进上下文 | MRR | 无答案时塞进 | 平均塞进 |
|---|---|---|---|---|---|---|
| 基线 | 69% | 88% | 88% | 0.79 | 12 | 12 |
| + 改写检索词、向量文字带元数据 | 74% | 90% | 90% | 0.82 | 12 | 12 |
| + 相关度门槛、原文兜底 | 79% | 90% | 90% | 0.85 | 0.7 | 1.5 |
| + 调打分权重、点名的人放宽门槛 | 93% | 95% | 95% | 0.94 | 0.7 | 2.2 |
| + 模型重排（重排决定留哪些） | 95% | 98% | 98% | 0.96 | 0 | 1.0 |
| 同上再跑一次 | 90% | 90% | 90% | 0.90 | 0 | 1.0 |
| **最终：重排只往前排和往回捞，门槛放行的照样保留** | **98%** | **100%** | **100%** | **0.99** | 0.7 | 2.2 |

「重排决定留哪些」不稳定：同样的输入，模型偶尔返回空列表，把明摆着的答案也删了。两次运行丢的还不是同一条（一次丢了「血压药」，一次丢了另外 4 条）。所以最终的分工是：**哪些能进上下文由分数门槛决定（结果稳定），重排只负责把真正相关的往前排，并把被门槛误杀的捞回来**。这样最差也和只用门槛一样。
